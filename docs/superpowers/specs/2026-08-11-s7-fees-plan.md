### B0 — Domain groundwork — DONE (2026-08-11)

- `Tenant` gains `gstin`/`legal_name`/`billing_address` (nullable — no
  settings UI yet, just the columns). `Batch.instalment_plan` is additive
  (nullable JSONB) — every existing batch keeps working with no plan at
  all. `Enrolment::STATUSES` gains `'pending_payment'` (PHP-side const
  only, no migration — the column is already a plain `string`).
- Five migrations, in FK-dependency order:
  `..._200000_add_billing_columns_to_tenants_table`,
  `..._200001_add_instalment_plan_to_batches_table`,
  `..._200002_create_fee_coupons_table` (created *before* `fee_invoices`,
  since `fee_invoices.coupon_id` references it — got this order right on
  the first attempt by planning the FK graph before naming files, not by
  fixing a migrate failure after the fact),
  `..._200003_create_fee_invoices_table`,
  `..._200004_create_fee_payments_table`.
- Three models (`FeeCoupon`, `FeeInvoice`, `FeePayment`), each
  `BelongsToTenant`, no soft-deletes for any of them — unlike `Question`
  (S6 B0), nothing in this domain's own schema references these rows by a
  loose, non-FK-enforced pointer the way `quiz_attempts.question_ids`
  (JSON) does; every reference here is a real FK, so a hard delete's
  cascade is the correct, enforced behaviour, not a gap to guard against
  later the way S6 B8 found `Quiz`'s missing soft-deletes to be.
- `PaymentProvider` interface (`createOrder(FeeInvoice): array{order_id,
  amount, currency}`, `verifyWebhookSignature(string, string): bool`) +
  `FakeRazorpayDriver` (bound in `AppServiceProvider`, hash-seeded
  deterministic order ids, same shape as `FakeAiDriver`/
  `FakeLiveClassDriver`) + real `RazorpayProvider` (built, unbound — no
  live account yet). Unlike `ZoomVideoSdkProvider` (JWT-only, no outbound
  call), a real Razorpay order genuinely requires an HTTP call to
  Razorpay's Orders API — built for real against `Http` and unit-tested
  with `Http::fake()`, not stubbed out. Both credential-gated methods
  (`createOrder()`, `verifyWebhookSignature()`) throw `RuntimeException`
  with the same "this is exactly why it isn't bound yet" message
  `ZoomVideoSdkProvider` uses when `RAZORPAY_KEY_ID`/`_SECRET`/
  `_WEBHOOK_SECRET` aren't configured. `config/services.php` gained a
  `razorpay` entry; `.env.example` gained the three placeholders, matching
  the `ZOOM_SDK_KEY`/`ZOOM_SDK_SECRET` precedent.
- Registered all three in `TenantModelRegistry::MODELS` **in this block**
  with full `seedAttributes()`/`updateAttributes()` — same "mandatory now,
  not deferrable" confirmation S6 B0 already established.
  `FeeInvoice`/`FeePayment`'s seed fixtures nest a fresh
  Course→Batch(→Enrolment) per FK field rather than sharing one instance
  across fields, matching this registry's own established looseness
  (`BatchSession`'s existing fixture does the same for its `lesson_id` vs
  `batch_id` — `CrossTenantTest` only needs valid, distinct FK targets,
  not a business-coherent scenario).
- **Real gap caught by the first test run, not assumed away**: two model
  tests asserted a DB-level `default()` (`FeeCoupon.status`,
  `FeePayment.provider`) would show up on the in-memory model returned by
  `create()` without passing it explicitly — it doesn't. Postgres inserts
  through Eloquent's `create()` only return the auto-increment id, not
  every column's resolved default, so an unset attribute reads back as
  `null` in memory until the model is re-fetched. This matches every
  existing fixture in this codebase (`Question`/`Quiz`/etc. always pass
  `status` explicitly in `create()` calls — confirmed by reading them, not
  assumed) — fixed the two tests to assert against `->fresh()` instead,
  which is also the more meaningful test: it actually proves the DB
  default fires, rather than trivially echoing back a value the test
  itself supplied.
- `composer test`: 369/370 passing (13 new — `FeeModelsTest`,
  `FakeRazorpayDriverTest`, `RazorpayProviderTest`, +3 in the generated
  `CrossTenantTest` suite), same 1 pre-existing `CourseSlugUniquenessTest`
  failure, unrelated.

### B1 — Order creation (P1) — DONE (2026-08-11)

- **Resolved an architecture gap the design doc left half-addressed.**
  Decision 3 (§2.4) only worked out the Fees→Batches direction (payment
  capture finalizes an enrolment via an event, not a direct service call).
  B1 needed the *reverse* direction — Batches triggering Fees to create an
  invoice at the moment of enrolling — and the same rule applies
  symmetrically: `BatchEnrolmentService` (Batches) can't call
  `FeeInvoiceService` (Fees) directly either. Fixed with a new
  `Batches\Events\EnrolmentAwaitingPayment` (same `(int $enrolmentId, int
  $tenantId)` shape as `StudentEnrolled`/`SeatReleased`), a
  `Fees\Listeners\CreateInvoiceForPendingEnrolment` that's the only thing
  that turns it into a real `FeeInvoice`, wired in `AppServiceProvider`
  alongside the app's other cross-domain `Event::listen()` calls. Batches
  ends this block still not knowing Fees exists — same one-way-ignorance
  shape decision 3 already established, just the other direction.
- `BatchEnrolmentService::enrol()` — pulled the `manual_only` refusal out
  of the `match`'s `default` arm into an early guard (so a *paid*
  `manual_only` batch refuses self-service the same way a free one
  already does, without duplicating the check), then added the `is_paid`
  branch: `enrolPendingPayment()` creates the enrolment as
  `pending_payment` with `source` set to whatever `self_enrol_mode` would
  have produced (B2's payment-capture listener reads that back to decide
  whether to finalize into `active` or `pending_approval`), and dispatches
  `EnrolmentAwaitingPayment` — both wrapped in one `DB::transaction()` so a
  listener failure can't strand an enrolment with no invoice to pay.
  Existing free-batch behavior confirmed unchanged by re-running every
  existing `BatchEnrolmentServiceTest`/`BatchCatalogTest` case unmodified,
  not just adding new ones alongside them.
- `FeeInvoiceService::invoiceFor(Enrolment): FeeInvoice` — built against a
  single full-amount invoice only (took the plan's own offered shortcut
  rather than guessing B4's instalment-split shape ahead of time). Sequence
  numbering (`sequence_number`/`invoice_number` are both `NOT NULL` from
  B0's migration, so this couldn't be deferred to B5 as the plan's own B5
  note implied — pulled forward out of necessity, documented here rather
  than silently done) locks the *tenant* row before reading
  `MAX(sequence_number)`, not the aggregate query itself — Postgres refuses
  `FOR UPDATE` combined with an aggregate function, so the lock has to sit
  on a real row, same shape `BatchEnrolmentService::enrolDirect()` already
  uses (lock the parent, then run an ordinary read inside that lock).
  `invoice_number` format: `INV-{tenant}-{FY}-{sequence}`, Indian financial
  year (April-March). `gstin_snapshot` copies the tenant's GSTIN at issue
  time — regression-tested that changing the tenant's GSTIN afterward
  doesn't rewrite the historical invoice.
- `FeeInvoiceService::createPaymentOrder(FeeInvoice): FeePayment` — calls
  `PaymentProvider::createOrder()` and persists the resulting
  `provider_order_id` as a `FeePayment` row (`status='created'`,
  `idempotency_key` a fresh UUID) — this is the row B2's webhook will find
  by `provider_order_id` and flip to `captured`, not something B2 creates
  itself.
- `FeeCheckout` (`app/Livewire/`, shared — not
  `app/Domains/Fees/Livewire/`, deliberately, so it can read both
  `Enrolment` and `FeeInvoice` directly without either domain calling the
  other's service) embeds into `batch-catalog.blade.php`'s existing
  per-row status branch, alongside the `waitlisted`/`pending_approval`
  branches already there — verified (not assumed) `BatchCatalog::join()`
  and `render()` needed zero changes themselves, since `render()` already
  re-queries the enrolment fresh on every render and the Blade view just
  needed one more `@elseif` arm. `startCheckout()` only gets as far as
  "order exists, ready for a real checkout widget" — actual capture is
  B2's job entirely.
- `composer test`: 382/383 passing (13 new — 6 added to
  `BatchEnrolmentServiceTest`, `FeeInvoiceServiceTest` (5),
  `FeeCheckoutTest` (2)), same 1 pre-existing `CourseSlugUniquenessTest`
  failure, unrelated.

### B2 — Webhook capture + auto-enrolment on payment (P5) — DONE (2026-08-11)

- **The plan's own idempotency note was imprecise, corrected at build
  time.** `fee_payments.idempotency_key` (a UUID generated in B1 when we
  create the order) isn't what makes the *webhook handler* safe to call
  twice — it was never meant to be looked up from an inbound payload,
  Razorpay doesn't echo it back. The real guard is simpler and more
  standard: `PaymentReconciler::capture()` looks up the `FeePayment` by
  `provider_order_id` (which *is* in the payload) under `lockForUpdate()`,
  and no-ops if it's already `status = 'captured'` — the same
  re-check-under-lock TOCTOU discipline every scheduled sweep in this app
  already uses, just triggered by an inbound request instead of a cron
  tick. `idempotency_key`'s real intended use — an outbound
  `Idempotency-Key` header on the *create-order* API call, so a
  double-clicked "Pay now" doesn't create two Razorpay orders — is still
  unwired (`RazorpayProvider::createOrder()` doesn't send it). Flagged, not
  silently fixed here: it's a different idempotency concern (client-side
  double-submit) from what this block's own scope (webhook processing)
  needed to solve, and a legitimate fast-follow rather than a B2 blocker.
- Confirmed (not assumed) that `CurrentTenant` binding doesn't leak across
  requests the way S6 B7's sweep could leak across loop iterations — each
  HTTP request is Laravel's own fresh container resolution, so this risk
  genuinely doesn't apply here; no `withoutGlobalScope('tenant')`-style
  workaround was needed. Signature is verified *before* a single payload
  field is trusted for anything, including which tenant to resolve — an
  unverified payload's own `notes.tenant_id` must never be trusted enough
  to bind `CurrentTenant`, let alone write a row.
- `RazorpayWebhookController` (`routes/api.php`, `POST /api/webhooks/razorpay`,
  no tenant domain constraint) does no business logic itself — extracts
  the raw body + `X-Razorpay-Signature` header and hands both to
  `PaymentReconciler::reconcile()`, which owns everything from signature
  verification onward (design doc §3.0's own file tree). Also handles
  `payment.failed` (not just `.captured`) — a failed attempt updates the
  `FeePayment` to `status = 'failed'` with a reason, never touches the
  `FeeInvoice` (stays `pending`), so `FeeCheckout`'s existing "Try again"
  path (already built in B1, unused until now) can create a fresh order
  against the same invoice.
- **Two real bugs found by the retry-on-failure test itself, not assumed
  away**:
  1. `FakeRazorpayDriver::createOrder()` (B0) generated its fake
     `order_id` purely from the invoice's own id + amount — deterministic
     *by design* at the time, matching `FakeLiveClassDriver`'s own
     reproducible-fixture shape. That determinism actively breaks a retry:
     two `FeePayment` attempts against the *same* invoice got the *same*
     `provider_order_id`, so `PaymentReconciler` could no longer tell them
     apart — a real Razorpay order id is unique per API call even for an
     identical amount, so this was a fake-driver artifact, not a design
     flaw in the reconciler. Fixed by folding `uniqid('', true)` into the
     hash input; updated the one B0 test that had asserted the old
     (now-wrong) determinism.
  2. A day-granularity expiry test (`finalizePendingPayment()`'s
     `pending_approval` branch, 7-day window) failed by exactly one day —
     `expires_at` round-trips through Eloquent's `datetime` cast as a
     string on write (no microseconds), so a fresh in-memory `now()` in
     the test sits a fraction of a second ahead of the persisted value;
     `diffInDays()` then floors an almost-but-not-quite-7.0 span down to
     6. Not a bug in the service (the free-batch equivalent test already
     avoided this by diffing two *equally-truncated* timestamps against
     each other) — fixed the test to compare calendar dates
     (`->toDateString()`), which is what "expires in 7 days" actually
     means here and sidesteps the precision mismatch entirely.
- `BatchEnrolmentService::finalizePendingPayment(Enrolment): Enrolment` —
  the only thing that ever resolves a `pending_payment` row onward, called
  by `FinalizeEnrolmentOnPaymentCaptured` (Batches' own listener for
  Fees' `PaymentCaptured` event — same one-way-ignorance shape as B1's
  `EnrolmentAwaitingPayment`, just the other direction). Reads `source`
  (set back in B1's `enrolPendingPayment()`) to decide `active`/
  `waitlisted` (direct) vs `pending_approval` (approval, fresh 7-day
  window starting from payment time, not the original enrol attempt). The
  direct branch shares `resolveDirectStatus()` with `enrolDirect()` rather
  than re-deriving the seat-vs-waitlist decision — extracted from
  `enrolDirect()` in this block specifically so the two can't drift.
  A status other than `pending_payment` is a no-op, so a duplicate/late
  `PaymentCaptured` (however unlikely, given `capture()`'s own idempotency)
  can never re-finalize an already-settled enrolment.
- **Known, documented gap, not silently designed around**: after a webhook
  captures a payment, `FeeCheckout`'s own Livewire state doesn't
  automatically refresh — the webhook is a separate HTTP request from the
  student's browser session, so the UI only reflects the new
  active/pending_approval status on the student's next page load/action.
  No `wire:poll` or redirect-based refresh was built for this — real-time
  UI update is a polish concern outside this block's backend-correctness
  scope, flagged here as a fast-follow candidate.
- `composer test`: 396/397 passing (14 new — `PaymentReconcilerTest` (7),
  `RazorpayWebhookControllerTest` (2), 4 added to
  `BatchEnrolmentServiceTest`, 1 net added to `FakeRazorpayDriverTest`),
  same 1 pre-existing `CourseSlugUniquenessTest` failure, unrelated.

### B3 — Coupon codes (P2) — DONE (2026-08-11)

- **Where a coupon gets applied wasn't actually settled by the design
  doc — decided at build time.** The invoice already exists by the time a
  student reaches checkout (created automatically at `enrol()` time, B1),
  so redemption couldn't happen at invoice-creation the way the plan's own
  title implied without threading a coupon-code field through
  `BatchCatalog::join()` and the `EnrolmentAwaitingPayment` event —
  coupling the Batches-domain join button to a purely Fees-domain concept.
  Instead, `FeeCheckout` (already the right shared component per B1) gained
  a coupon-code input and an `applyCoupon()` action that *mutates* the
  already-created invoice's `discount_amount`/`gst_amount`/`total_amount`
  before payment. `FeeInvoice.coupon_id` being a single nullable FK (from
  B0) makes "one coupon per invoice, applied once" the natural shape —
  `applyCoupon()` refuses a second call once `coupon_id` is already set.
- `FeeInvoiceService::applyCoupon(FeeInvoice, FeeCoupon)` — discount is
  computed against the pre-tax `amount`, not the already-taxed
  `total_amount`: standard GST practice is discount-then-tax, not a
  straight cut off the tax-inclusive total. `amount` itself is never
  rewritten (the batch's real sticker price stays on the record for
  audit); only `discount_amount`, `gst_amount`, and `total_amount` change.
  A fixed-type discount is capped at the invoice's own `amount` so the
  total can never go negative. Validates tenant match implicitly (`FeeCoupon`
  is `BelongsToTenant`, so a cross-tenant code simply doesn't resolve — no
  explicit check needed), `status = active`, not expired,
  `used_count < usage_limit` when set, invoice still `pending`, and no
  coupon already applied — one shared `CouponNotRedeemableException`
  (reason as the message) rather than four near-duplicate exception
  classes, since every case collapses to the same user-facing outcome.
  `used_count` increments under the same `lockForUpdate()` transaction
  that validates it, on the coupon row — matches
  `BatchEnrolmentService::enrolDirect()`'s own seat-race discipline exactly.
- `FeeCouponResource` (`/admin`, not `/teach` — coupons are an institute-
  admin billing concern, matching design doc §3.0's own file tree) — plain
  CRUD, `code` upper-cased on save (`dehydrateStateUsing`) so redemption's
  case-insensitive lookup in `FeeCheckout` never depends on how the admin
  typed it. `DeleteAction` needed no guard the way `QuizResource`'s did in
  S6 B8 — `fee_invoices.coupon_id` is `nullOnDelete()` (set correctly back
  in B0), not `cascadeOnDelete()`, so removing a coupon safely nulls the
  reference on any invoice it was once applied to rather than destroying
  invoice history.
- `composer test`: 409/410 passing (13 new — 8 added to
  `FeeInvoiceServiceTest`, 3 added to `FeeCheckoutTest`,
  `FeeCouponResourceTest` (2)), same 1 pre-existing
  `CourseSlugUniquenessTest` failure, unrelated.

### B4 — Instalment plans (P3) — DONE (2026-08-11)

- **`Batch.instalment_plan` was a column with nothing behind it until this
  block** — B0's migration added it, but nobody had ever added it to
  `Batch::$fillable`/`casts()`, so the Filament form couldn't have saved
  it even after the Repeater went in. Same "pinned but unused" pattern
  this whole design doc opened by naming (`Lesson.type='quiz'` before S6,
  `seed_questions` before S6) — closed here, not carried forward.
- `FeeInvoiceService::invoiceFor()` renamed to `invoicesFor()`, returning
  a `Collection` — the plan's own B1 note already flagged this rename as
  likely once B4 landed. One invoice if `Batch.instalment_plan` is empty
  (unchanged full-fee behaviour, regression-tested), N if it's set, one
  per plan line. **The parts are made to sum exactly back to the whole**:
  splitting a price by raw percentage risks a paise short/over (three
  33.33% lines on ₹100 leave 1 paise unaccounted for), so the *last* line
  absorbs whatever's left rather than its own literal percentage —
  regression-tested with a 33/33/34 split. Each instalment gets its own
  GST computed on *its own* share, not the full price (a real distinction
  worth its own test, not just trusted by symmetry). `days_after_enrolment`
  offsets `due_date` from `now()` at invoice-creation time, per line.
- **`FeeCheckout::currentInvoice()` had a real bug, exposed the moment a
  second pending invoice could exist.** It picked `latest('id')`, which
  was harmless with exactly one invoice (B1-B3's whole world) but wrong
  the moment instalments introduced a second: `latest('id')` surfaces the
  *last-created* row, not the *earliest-due* one, so a student would have
  been shown instalment 2 before instalment 1. Found while reasoning
  through B4's own consequences, not by a failing test first — fixed to
  order by `due_date` (earliest first) before building the regression
  test, which then passed on the first run against the fix.
- `BatchResource`'s form gained the `instalment_plan` `Repeater`
  (percent + days-after-enrolment per line), gated behind `is_paid` like
  `price` already is. **First custom validation closure in this
  codebase's Filament forms** ("percentages sum to 100" has no built-in
  rule) — and it broke on the first attempt for a reason worth recording:
  `->rule()` closures are evaluated through Filament's own
  dependency-injecting `evaluate()` (the same mechanism `->visible()`/
  `->required()` use), not handed straight to Laravel's validator. Passing
  a plain `(string $attribute, $value, Closure $fail)` closure directly —
  the standard *Laravel* in-line rule shape — fails immediately: Filament
  tries to dependency-inject a parameter named `$attribute` and finds
  nothing by that name. The fix is a closure-that-returns-a-closure: the
  outer one takes no params (or Filament's own recognized ones, like
  `Get $get`), and *returns* the Laravel-shaped validation closure, which
  is what actually gets registered. Confirmed by running it, not guessed
  from documentation.
- Whether a coupon (B3) should discount a whole instalment plan
  proportionally or just the one invoice it's redeemed against was an open
  question B3's own comment implicitly assumed away ("B4 splits the
  post-discount total"). Resolved here: a coupon discounts *only the
  invoice it's applied to* — B4 splits the batch's raw price at enrolment
  time, before any coupon exists to redeem (coupons are applied afterward,
  in `FeeCheckout`, specifically so Batches' `enrol()` flow never has to
  know coupon codes exist — B3's own decision, not revisited here).
  Documented on `applyCoupon()` itself, correcting the stale forward
  reference left there since B3.
- "Only the first-due invoice blocks enrolment finalization" (design doc
  §2.4 decision 4) needed **no new code at all** — `finalizePendingPayment()`
  (B2) already no-ops once the enrolment isn't `pending_payment` anymore,
  so whichever instalment happens to capture first finalizes the
  enrolment, and every later instalment's own `PaymentCaptured` event
  finds nothing left to do. B2's own idempotency guard turned out to
  already be exactly the mechanism this decision needed.
- `composer test`: 417/418 passing (8 new — 5 added to
  `FeeInvoiceServiceTest`, 1 added to `FeeCheckoutTest`, 2 added to
  `BatchResourceTest`), same 1 pre-existing `CourseSlugUniquenessTest`
  failure, unrelated. Ran via `php artisan test` directly — composer's own
  process-timeout wrapper is now shorter than the full suite's runtime.

### B5 — GST-compliant invoices + receipts (P4) — DONE (2026-08-11)

- **Half of this block's own scope had already been built and shipped in
  B1**, out of necessity — `sequence_number`/`invoice_number` are `NOT
  NULL` columns from B0, so B1 couldn't create a valid `FeeInvoice` row
  without a working, race-safe numbering scheme, and `gstin_snapshot`
  the same. Both were already regression-tested there (sequence
  monotonicity, invoice-number format, GSTIN immunity to a later tenant
  change). B5's real remaining job was the thing nothing had built yet:
  somewhere a student (or staff) can actually *see* an invoice.
- **No genuine concurrent-lock test for `sequence_number` was written
  here either, same call as B1** — this Pest suite runs on one DB
  connection, so a `DB::listen()`-based race (the trick
  `ExpirePendingEnrolments`/`AutoSubmitExpiredQuizAttempts` use elsewhere
  in this app) only proves "re-check after acquiring the lock," not "two
  truly concurrent transactions can't both pass the lock." There's no
  stale-read bug class to regression-test here by construction — the code
  reads `MAX(sequence_number)` *after* the tenant-row lock, not before —
  and Postgres's own row-lock guarantee isn't something a same-connection
  test could disprove anyway. A genuine multi-connection test is possible
  in Laravel but has no precedent anywhere in this app and wasn't
  introduced for one block.
- `DownloadInvoiceController` (`GET /invoices/{invoice}`, `routes/fees.php`,
  tenant-scoped) — owner-or-staff gate, same shape every other per-record
  gate in this app uses (not a role check alone: a different student
  guessing an adjacent invoice id must not see someone else's fee record).
  Renders `resources/views/fees/invoice.blade.php`: GSTIN (or "Not
  registered" — most tenants have no settings UI to fill it in yet, so
  this is the common case, not an edge case), invoice number and date,
  due date and status, tenant `legal_name`/`billing_address` (falling back
  to plain `name` if unset), student name/email, description, an HSN/SAC
  placeholder (`9992`, education services — a real SAC lookup is out of
  scope), taxable value, discount + coupon code when one was applied, GST
  rate/amount, and total. Plain HTML with a `window.print()` button — no
  new PDF dependency, per design doc §2.4.5.
- `FeeCheckout` gained an invoice-history list (every invoice the
  enrolment has ever had, not just the currently-pending one) with a
  "View / print" link per row — a paid instalment's receipt needed to
  stay reachable after it stopped being the "current" invoice, which
  `currentInvoice()` alone could never surface again once its status left
  `pending`.
- `composer test`'s own 300s process-timeout wrapper remains shorter than
  the full suite's real runtime (~350s now, still climbing) — ran
  `php artisan test` directly again, no code change, flagged for B7 to
  either raise the wrapper's timeout or accept running the two

### B6 — Fee defaulter list + reminders (P7) — DONE (2026-08-11)

- `FlagOverdueInvoices` — a single bulk `UPDATE ... WHERE status =
  'pending' AND due_date < today`, no lock. Same reasoning
  `ExpirePendingEnrolments` established: the WHERE clause is re-evaluated
  atomically as part of the one UPDATE statement, so a payment captured in
  the same instant the sweep runs simply won't match — no fetch-lock-write
  dance needed, because this job creates nothing and has no per-row side
  effect beyond the column it's already writing. Boundary is exclusive
  (`due_date < today`, not `<=`): a row due exactly today stays `pending`
  through its "due today" reminder day and only flips to `overdue` the day
  after.
- `SendFeeReminders` — three stateless date-arithmetic queries per run
  (`due_date` = today+3 → `upcoming`, today → `due_today`, today-3 →
  `overdue`), matching against `whereIn('status', ['pending', 'overdue'])`.
  Stateless was the plan's own preferred option and it worked cleanly: an
  offset relative to a fixed `due_date` can only be true on exactly one
  calendar day under normal once-daily scheduling, so no persisted
  "already sent" flag was needed. Caveat carried forward, not silently
  dropped: if the scheduler somehow fires this job twice in the same day,
  the same reminder goes out twice — accepted, not guarded against, same
  spirit as B2's already-documented gaps.
  `bootstrap/app.php` registers `FlagOverdueInvoices` before
  `SendFeeReminders` in the schedule (both `->daily()`) specifically so a
  row crossing into `overdue` on a given run is picked up by that same
  run's T+3 "overdue" reminder query, which matches on `due_date` alone
  and doesn't itself re-check status beyond the `whereIn`.
